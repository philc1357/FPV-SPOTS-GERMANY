What is Intruder

Intruder ist Burp Suites eingebautes Fuzzing-Tool. Es erlaubt die automatisierte Modifikation von Requests und repetitives Testen mit variierenden Eingabewerten. Dabei wird ein Basis-Request erfasst und dann in mehreren Variationen an das Ziel gesendet.

Typische Einsatzgebiete

  • Brute-Force von Login-Formularen – Username- und Passwort-Felder mit Wordlists durchprobieren
  • Fuzzing – Subdirectories, Endpoints oder virtuelle Hosts enumerieren
  • Parameter-Manipulation – Eingabewerte systematisch verändern und Reaktionen analysieren

Die Funktionalität ist vergleichbar mit Kommandozeilen-Tools wie wfuzz oder ffuf, bietet aber den Vorteil der direkten Integration in Burp Suite.

Die vier Hauptbereiche

Tab Funktion
Positions Angriffstyp wählen und Payload-Positionen im Request markieren
Payloads Payload-Sets, Wortlisten und Verarbeitungsregeln konfigurieren
Resource Pool Threading und Ressourcenverwaltung (nur Pro)
Settings Erweiterte Optionen wie Grep-Match, Redirects und Fehlerbehandlung
Hinweis: Die Community Edition von Burp Suite ist in Intruder rate-limited. Angriffe laufen deutlich langsamer als in der Professional Edition. Für echte Pentests ist die Pro-Version oder ein Kommandozeilen-Tool wie ffuf empfehlenswert.

Positions

Im Positions-Tab wird festgelegt, wo im Request die Payloads eingesetzt werden sollen. Positionen werden durch das §-Zeichen (Section-Symbol) markiert. Alles zwischen zwei §-Zeichen wird durch den jeweiligen Payload ersetzt.

Steuerungselemente

Button Funktion
Add § Markierten Text als Payload-Position definieren
Clear § Alle definierten Positionen entfernen
Auto § Automatisch wahrscheinliche Positionen erkennen (z.B. Parameter-Werte)

Beispiel

POST /login HTTP/1.1
Host: example.thm
Content-Type: application/x-www-form-urlencoded

username=§admin§&password=§password123§

In diesem Beispiel werden admin und password123 als Payload-Positionen markiert. Je nach gewähltem Angriffstyp werden diese Positionen unterschiedlich mit Payloads befüllt.

Tipp: Nutze immer zuerst Clear §, um die Auto-Markierungen zu entfernen, und setze dann manuell nur die gewünschten Positionen. So vermeidest du unnötige Payload-Positionen.
What symbol defines the start and the end of a payload position? Antwort: §
4

Payloads

Der Payloads-Tab ist in mehrere Bereiche unterteilt und erlaubt die detaillierte Konfiguration dessen, was an die markierten Positionen gesendet wird.

Payload Sets

Hier wird ausgewählt, welche Position konfiguriert wird und welcher Typ von Payload-Set verwendet werden soll. Die wichtigsten Typen:

  • Simple list – Manuelle Eingabe oder Laden einer Wortliste
  • Runtime file – Wortliste wird zur Laufzeit geladen (speichereffizient bei großen Listen)
  • Numbers – Numerischer Bereich (von, bis, Schrittweite)
  • Brute forcer – Generiert alle Kombinationen aus einem Zeichensatz

Payload Settings

Kontextabhängige Optionen je nach gewähltem Payload-Typ. Bei Simple list z.B. das Laden einer externen Wortliste oder manuelle Eingabe einzelner Payloads.

Payload Processing

Definiert Regeln, die auf jeden Payload vor dem Senden angewandt werden:

  • Add prefix/suffix – Zeichen vor/nach dem Payload anfügen
  • Match/Replace – Teile des Payloads ersetzen
  • Encode/Decode – Base64, URL-Encoding etc.
  • Hash – Payload hashen (MD5, SHA-1 usw.)
  • Skip if matches regex – Payloads nach Muster überspringen

Payload Encoding

Standardmäßig URL-encoded Burp Suite bestimmte Sonderzeichen (&, = etc.). Hier kann dieses Verhalten angepasst oder deaktiviert werden.

Which payload type lets us load a list of words from an external file? Antwort: Simple list
Which Payload Processing rule could we use to add characters at the end of each payload in the set? Antwort: Add suffix

Introduction to Attack Types

Burp Suite Intruder bietet vier verschiedene Angriffstypen. Jeder eignet sich für unterschiedliche Szenarien und unterscheidet sich darin, wie die Payloads auf die definierten Positionen verteilt werden.

Sniper

Einzelner Payload-Set, Positionen werden nacheinander durchlaufen. Standard-Angriffstyp.

Battering Ram

Einzelner Payload-Set, identischer Payload wird gleichzeitig an alle Positionen eingesetzt.

Pitchfork

Mehrere Payload-Sets, synchron durchlaufen – Element 1 aus Set 1 + Element 1 aus Set 2 usw.

Cluster Bomb

Mehrere Payload-Sets, alle möglichen Kombinationen werden getestet (kartesisches Produkt).

Sniper

Sniper ist der Standard-Angriffstyp und der am häufigsten verwendete. Er arbeitet mit einem einzigen Payload-Set und setzt jeden Payload nacheinander in jede definierte Position ein – während alle anderen Positionen ihren Standardwert behalten.

Funktionsweise

Bei zwei Positionen und einer Wortliste [burp, suite, intruder]:

Request 1: username=burp & password=password123 ← Position 1, Payload 1 Request 2: username=suite & password=password123 ← Position 1, Payload 2 Request 3: username=intruder& password=password123 ← Position 1, Payload 3 Request 4: username=admin & password=burp ← Position 2, Payload 1 Request 5: username=admin & password=suite ← Position 2, Payload 2 Request 6: username=admin & password=intruder ← Position 2, Payload 3

Berechnung der Requests

Anzahl Requests = Anzahl Payloads × Anzahl Positionen

Im Beispiel: 3 Payloads × 2 Positionen = 6 Requests.

Einsatzgebiete

  • Passwort-Brute-Force bei bekanntem Benutzernamen
  • API-Endpoint-Fuzzing
  • Einzelne Parameter-Werte durchprobieren
If you were using Sniper to fuzz three positions in a request, with a wordlist containing 100 words, how many requests would Intruder need to send to complete the attack? Antwort: 300
How many sets of payloads does Sniper use? Antwort: 1
7

Battering Ram

Battering Ram verwendet ebenfalls einen einzigen Payload-Set, setzt aber – im Gegensatz zu Sniper – den gleichen Payload gleichzeitig in alle definierten Positionen ein.

Funktionsweise

Bei zwei Positionen und einer Wortliste [burp, suite, intruder]:

Request 1: username=burp & password=burp ← Payload 1 in beide Positionen Request 2: username=suite & password=suite ← Payload 2 in beide Positionen Request 3: username=intruder & password=intruder ← Payload 3 in beide Positionen

Berechnung der Requests

Anzahl Requests = Anzahl Payloads

Im Beispiel: 3 Payloads = 3 Requests (unabhängig von der Anzahl der Positionen).

Einsatzgebiete

  • Race Condition Testing
  • Testen, ob der gleiche Wert an mehreren Stellen akzeptiert wird
  • Credential Stuffing, wenn Username = Passwort vermutet wird
As a hypothetical question: you need to perform a Battering Ram Intruder attack on the example request above. If you have a wordlist with two words in it (admin and Guest) and the positions were set as: username=§pentester§&password=§Expl01444t§ – what would the body of the first request that Battering Ram sends be? Antwort: username=admin&password=admin
8

Pitchfork

Pitchfork funktioniert wie mehrere gleichzeitige Sniper-Angriffe. Es werden mehrere Payload-Sets verwendet (eines pro Position, maximal 20) und synchron durchlaufen: Element 1 aus Set 1 wird mit Element 1 aus Set 2 kombiniert usw.

Funktionsweise

Set 1 (Usernames): [joel, harriet, alex]
Set 2 (Passwords): [J03l, Emma1815, Sk1ll]

Request 1: username=joel & password=J03l ← Element 1 aus beiden Sets Request 2: username=harriet & password=Emma1815 ← Element 2 aus beiden Sets Request 3: username=alex & password=Sk1ll ← Element 3 aus beiden Sets

Berechnung der Requests

Anzahl Requests = Länge des kürzesten Payload-Sets
Wichtig: Intruder stoppt, sobald das kürzeste Payload-Set aufgebraucht ist. Daher sollten alle Sets idealerweise die gleiche Länge haben.

Einsatzgebiete

  • Credential Stuffing – Bekannte Username:Passwort-Paare testen (z.B. aus einem Datenbank-Leak)
  • Korrelierte Daten – Wenn Position 1 und Position 2 logisch zusammengehören
What is the maximum number of payload sets we can load into Intruder in Pitchfork mode? Antwort: 20
9

Cluster Bomb

Cluster Bomb ist der intensivste Angriffstyp. Er testet alle möglichen Kombinationen aller Payload-Sets (kartesisches Produkt). Jedes Element aus Set 1 wird mit jedem Element aus Set 2 kombiniert usw.

Funktionsweise

Set 1 (Usernames): [joel, harriet, alex]
Set 2 (Passwords): [J03l, Emma1815, Sk1ll]

Request 1: username=joel & password=J03l Request 2: username=joel & password=Emma1815 Request 3: username=joel & password=Sk1ll Request 4: username=harriet & password=J03l Request 5: username=harriet & password=Emma1815 Request 6: username=harriet & password=Sk1ll Request 7: username=alex & password=J03l Request 8: username=alex & password=Emma1815 Request 9: username=alex & password=Sk1ll

Berechnung der Requests

Anzahl Requests = |Set 1| × |Set 2| × … × |Set n|

Im Beispiel: 3 × 3 = 9 Requests.

Achtung: Die Anzahl der Requests explodiert schnell! Eine Wortliste mit 100 Usernamen und 1000 Passwörtern erzeugt bereits 100.000 Requests. In der Community Edition mit Rate-Limiting dauert das extrem lange.

Einsatzgebiete

  • Credential Brute-Force – Wenn kein Zusammenhang zwischen Usernamen und Passwörtern bekannt ist
  • Vollständige Parameter-Kombinations-Tests
We have three payload sets. The first set contains 100 lines; the second contains 2 lines; and the third contains 30 lines. How many requests will Intruder make using a Cluster Bomb attack? Antwort: 6000

Practical Example

In diesem praktischen Beispiel wird eine grundlegende Intruder-Attacke Schritt für Schritt durchgeführt. Ziel ist es, ein Login-Formular auf der bereitgestellten TryHackMe-Maschine zu brute-forcen.

Schritt-für-Schritt Anleitung

1
Maschine starten & Proxy konfigurieren
Die TryHackMe-Maschine starten und sicherstellen, dass der Browser über den Burp-Proxy läuft. FoxyProxy oder die Proxy-Einstellungen des Browsers auf 127.0.0.1:8080 setzen.
2
Request abfangen
Das Login-Formular aufrufen und einen Login-Versuch durchführen. Den POST-Request im Proxy-Tab abfangen.
3
An Intruder senden
Rechtsklick auf den Request → „Send to Intruder“ (oder Ctrl+I).
4
Positionen konfigurieren
Im Positions-Tab Clear § klicken, dann nur die gewünschten Felder manuell mit Add § markieren.
5
Payloads laden
Im Payloads-Tab den Typ Simple list wählen und eine geeignete Wortliste laden (z.B. aus /usr/share/wordlists/).
6
Angriff starten
„Start Attack“ klicken und die Ergebnisse analysieren. Auffällige Responses (z.B. abweichende Status-Codes oder Längen) identifizieren.

Practical Challenge

In dieser Challenge geht es um eine IDOR-Schwachstelle (Insecure Direct Object Reference) in einem Support-Ticket-System. Ziel ist es, durch Manipulation von Ticket-IDs auf Tickets zuzugreifen, die einem anderen Benutzer gehören.

Vorgehensweise

1
Support-System aufrufen
Navigiere zum Support-Ticket-System auf der Zielmaschine unter http://MACHINE_IP/support/login. Logge dich mit den bereitgestellten Credentials ein.
2
Ticket-Request abfangen
Rufe ein existierendes Ticket auf und fange den GET-Request ab. Die URL enthält typischerweise eine Ticket-ID als Parameter, z.B. /support/ticket/1.
3
Intruder konfigurieren
Sende den Request an Intruder. Markiere die Ticket-ID als Position. Wähle Sniper als Angriffstyp. Payload-Typ: Numbers (z.B. von 1 bis 100, Schrittweite 1).
4
Ergebnisse analysieren
Starte den Angriff und sortiere die Ergebnisse nach Status-Code oder Response-Länge. Tickets mit einem 200 OK Status und abweichender Länge enthalten potenziell sensible Informationen anderer Benutzer.
IDOR erklärt: Eine IDOR-Schwachstelle liegt vor, wenn eine Anwendung Objekte (hier: Tickets) direkt über eine vorhersagbare Referenz (hier: fortlaufende IDs) zugreifbar macht, ohne zu prüfen, ob der aktuelle Benutzer berechtigt ist, auf dieses Objekt zuzugreifen.
Which attack type is best suited for this task? Antwort: Sniper
Configure an appropriate position and payload (the tickets are stored at values between 1 and 100), then start the attack. You should find that at least five tickets will be returned with a status code of 200. Look through the tickets, what is the flag? Antwort: THM{MTMxNTg5NTUzMWM0OWRlYzUzMDVjMzJl}

Extra Mile Challenge

Die Extra-Mile-Challenge geht einen Schritt weiter und erfordert den Einsatz von Makros in Burp Suite. Dies ist notwendig, wenn sich Cookies und Tokens bei jedem Request ändern (z.B. CSRF-Tokens oder Session-Cookies).

Warum Makros?

Viele moderne Web-Anwendungen verwenden Anti-CSRF-Tokens oder rotierende Session-Cookies. Wenn Intruder einen Request mit einem abgelaufenen Token sendet, wird dieser abgelehnt. Ein Makro löst dieses Problem, indem es vor jedem Intruder-Request automatisch einen vorherigen Request ausführt, um ein frisches Token zu erhalten.

Makro konfigurieren

1
Session Handling Rules
Gehe zu Settings → Sessions (oder Project options → Sessions). Unter „Session Handling Rules“ klicke auf „Add“.
2
Rule Actions
Im neuen Rule Editor unter „Rule Actions“ wähle „Run a macro“.
3
Makro definieren
Klicke auf „Add“ unter dem Macro Editor. Wähle aus der HTTP History den Request aus, der das frische Token liefert (typischerweise der GET-Request auf die Login-Seite). Bestätige mit „OK“.
4
Parameter-Handling
Konfiguriere, welche Cookies/Token-Parameter aus der Makro-Response extrahiert und in den Intruder-Request eingesetzt werden sollen. Aktiviere „Update current request with cookies from session handling cookie jar“.
5
Scope konfigurieren
Im „Scope“-Tab der Rule sicherstellen, dass die Regel für Intruder aktiviert ist und der URL-Scope zur Ziel-URL passt.
Tipp: Diese Technik ist nicht nur für Intruder relevant – Makros sind essenziell für jede Art von automatisiertem Testing gegen Anwendungen mit CSRF-Schutz oder Session-Management.
Navigate to http://MACHINE_IP/admin/login. Activate the macro and use Intruder to brute-force the login. What is the flag? Antwort: THM{NmNlZTYxNTk1NzRjOWQ1MDNkYzkyYjFl}
